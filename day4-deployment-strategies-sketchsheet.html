Deployment strategies & environments

How the industry actually ships changes without breaking prod for everyone at once — and what to do when it breaks anyway.

1

Blue-Green

  • Blue → the current live version
  • Green → the new version, running alongside, not yet public
  • Flip → switch traffic to Green, all at once
Blue: live Green: staged → test → flip →
Green: live Blue: standby
Tradeoff: rollback is instant — just flip back to Blue. Costs double: two full environments running at once.
2

Canary

  • Canary → named after coal-mine canaries, an early warning
  • Send a small slice of real traffic to the new version first
  • Watch error rates & metrics before widening it
5%
25%
100%
Tradeoff: catches real-world problems on a small blast radius, but is slower to fully roll out and needs traffic-splitting infrastructure.

  • Replace instances one (or a few) at a time
  • Old and new versions run side by side, briefly

Environments & Promotion

  • Dev → where you build and break things freely
  • Staging → a prod-like rehearsal, final check before real users
  • Prod → real users, real consequences
merge → develop → auto-deploy staging
tag a release → auto-deploy prod
Why bother: staging exists specifically to catch what dev can't — real-ish data, real-ish traffic patterns, without risking actual users.
5

Secrets Management

  • Env var / secret store → injected at runtime, never committed to code — this is exactly what RENDER_DEPLOY_HOOK already is in this project
  • Vault → a dedicated system (HashiCorp Vault, AWS Secrets Manager) for larger orgs — auto-rotates credentials, tightly access-controlled
  • never commit secrets to git
  • rotate them periodically
  • give each secret the least access it needs
  • confirm they're masked in logs
this is the "what if it breaks" answer 🚨 6

Rollback Strategies

  • Roll back → redeploy the last known-good version immediately
  • Roll forward → fix the bug and push a new deploy through the normal pipeline
  • git revert → undo the bad commit cleanly, then let the pipeline redeploy it
  • detect it (monitoring / alerts / health check failing)
  • decide: roll back or roll forward?
  • execute through the same pipeline — never by hand on the server
  • confirm health, then do the post-mortem

🎤 One-liners for the interview

Blue-Green: "Instant rollback, double the infrastructure cost."
Canary: "Small blast radius first, then widen once metrics look good."
Rolling: "The default almost everyone uses — no extra infra, but slower to undo."
Rollback: "Always through the pipeline, never a manual SSH fix on the live server."
